## 当前结论

不是画板问题。

不是中转站服务器性能问题。

不是 LK888 参数适配器再次坏掉：

- adapter.log 中仍能看到 `upstream_request_prepared`。
- 尺寸仍正确转成 `1728x2304` 或 `2304x1296`。
- 参考图压缩逻辑仍正常。

主要问题是：

1. LK888 GPT 图片上游当前生成耗时过高，平均约 187 秒，最慢接近 399 秒。
2. 老夜 GPT 图片当前可用，但常规耗时约 50-70 秒，不是秒出。
3. 如果客户很多并发生成，低价图片上游会出现排队，前端体感会更慢。

## 当前止血方案

保持：

```text
LK888 GPT channel #5 禁用
老夜 GPT channel #1 启用
```

理由：

- 老夜当前比 LK888 稳。
- LK888 当前做主路由会把客户拖到 2-6 分钟。
- 新请求先走老夜，客户大概率约 1 分钟内拿到结果。

不要现在做的事：

- 不要反复重启 New API。
- 不要改 LK888 尺寸映射。
- 不要改画板。
- 不要新增未测试渠道直接设最高优先级。
- 不要点 New API 后台图片渠道测试，可能真实扣费。

## 如果客户仍嫌 1 分钟慢

这不是中转站配置能直接解决的。

可选方案：

1. 接入第三个更快的 GPT 图片上游。
2. 保留老夜为主，LK888 仅在确认恢复到 60 秒内后再启用。
3. 后续把 GPT 图片改成异步任务体验：前端先显示排队/生成中，不要让用户以为卡死。
4. 开正式结果缓存代理，解决结果图 URL 下载慢的问题，但它不能缩短上游生图时间。
