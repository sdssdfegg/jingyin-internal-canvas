# 2026-08-21 香蕉 2 带图生成等待中转站超时

## 基本信息

- 编号：API-2026-08-21-001
- 首次发现时间：2026-08-21 凌晨
- 发现人：用户前端画板截图反馈
- 状态：处理中（2026-08-22 已完成香蕉路由拆分，待真实请求观察）
- 等级：P1
- 影响范围：香蕉 2、带参考图图片编辑、画板等待中转站返回

## 现象

- 画板表现：点击香蕉 2 带参考图生成，卡片显示失败。
- 画板报错：`等待中转站返回：图1 469 KB · 场景补充`，并提示生成超时。
- 对比现象：GPT 图像链路正常。
- 当前约束：不修改画板源码，优先在 API 中转站/上游适配层处理。

## 已确认事实

- New API 绘图日志里，历史 `nano-banana2` 真实带图任务走的是图片编辑链路：
  - 请求类型：图片编辑
  - 模型：`nano-banana2`
  - 历史渠道：老夜渠道 `1`
  - 历史耗时：约 `41s`、`68s`、`43s`
  - 任务状态：后台显示成功
- 7lai 渠道后台单渠道模型测试：
  - 渠道：`7lai-nano-banana-image`
  - 渠道 ID：`6`
  - 测试模型：`nano-banana2`
  - 测试结果：成功
  - 请求时长：约 `14.94s`
  - 但该测试覆盖的是图片生成端点，不等同于带参考图图片编辑端点。
- New API 渠道测试弹窗端点类型：
  - 有：`/v1/images/generations`
  - 未看到：`/v1/images/edits`
- New API 绘图设置：
  - `允许回调（会泄露服务器 IP 地址）`：关闭
  - `开启之后将上游地址替换为服务器地址`：关闭
  - `检测必须等待绘图成功才能进行放大等操作`：开启
- `7lai.py` 参考代码中，图片任务统一构造为：
  - 上游端点：`/v1/images/generations`
  - 带图参数：`image_url` / `image_urls`
  - 没有看到 `/v1/images/edits` 适配逻辑。

## 根因判断

初步根因：

- 画板带参考图的香蕉 2 请求走 OpenAI 标准图片编辑接口 `/v1/images/edits`。
- 7lai 参考适配逻辑走的是 `/v1/images/generations`，用 JSON 里的 `image_url/image_urls` 表达参考图。
- 因此，“7lai 的 `nano-banana2` 后台生成测试成功”不能证明“画板带图编辑请求也能成功”。
- 历史老夜带图任务耗时 40-70 秒，画板侧出现“等待中转站返回超时”，说明同步等待链路也存在超时风险。

## 风险

- 如果继续把 `nano-banana2` 强制优先路由到 7lai，而 7lai 不兼容 `/v1/images/edits`，画板带图任务会继续失败或超时。
- 如果直接开启 New API 回调，可能暴露中转站服务器 IP；需要用户确认后再改。
- 如果只提高画板超时时间，可以缓解等待超时，但不能解决 7lai 上游端点不兼容的问题。

## 建议修复方案

优先方案：

- 给 7lai 做一个上游适配层：接收 New API/画板的 `/v1/images/edits` 请求，提取上传图片并转成可访问 URL，然后调用 7lai 上游的 `/v1/images/generations`，把参考图放入 `image_url/image_urls`。
- New API 的 7lai 渠道 base_url 改为该适配层地址，而不是直接打 7lai 上游。

临时方案：

- 暂时不要让带参考图的 `nano-banana2` 优先走 7lai，避免 endpoint 不兼容造成批量失败。
- 继续让已验证可用的渠道承接带图香蕉请求，等 7lai edits 适配完成后再切最高优先级。

可选方案：

- 如果接受“暴露服务器 IP”的风险，可开启 New API 绘图设置里的 `允许回调`，再观察绘图日志是否能稳定获取结果。
- 如果画板可配置超时，建议把香蕉带图等待时间提高到至少 `120s`；历史任务已有 `68s` 的正常完成记录。

## 验证计划

1. 用画板发一次 `nano-banana2` 带参考图请求。
2. 查看 New API 绘图日志：
   - 渠道是否为目标渠道。
   - 类型是否为图片编辑。
   - 是否成功。
   - 花费时间是否超过画板等待时间。
3. 如果仍失败，查看使用日志/绘图日志是否有失败原因；若没有日志，说明请求可能在画板侧或网关前置层超时/中断。

### 进一步判断

结合现有证据，`7lai` 启用后仍走老夜，优先怀疑以下顺序：

1. 带图请求走的是 `/v1/images/edits`，但 `7lai` 上游适配更像是 `/v1/images/generations`；New API 可能判定 7lai 不适配或请求失败后，最终使用老夜。
2. `7lai` 的默认测试模型是 `nano-banana-pro`，而画板实际请求是 `nano-banana2`；测试成功不能证明实际 `nano-banana2` 带图链路可用。
3. 香蕉渠道的入口名没有像 GPT Image 一样统一：GPT Image 专用渠道都配置 `gpt-image -> gpt-image-2`，香蕉的 `code28` 没有 `nano-banana2 -> nano-banana-2`，老夜则直接支持 `nano-banana2`。
4. 如果请求时 `7lai` 曾经因失败被自动禁用或状态缓存未刷新，优先级 `200` 也不会生效。

结论：

- 这不是“渠道显示名称有横杠/没横杠”导致；渠道名称不参与模型路由。
- 关键是请求模型名、渠道模型列表、模型重定向、渠道启用状态、以及上游是否支持图片编辑接口。

### 建议统一规则

- 面向画板只保留一个入口模型名：建议统一用 `nano-banana2`，因为画板和历史日志已经在用它。
- 所有香蕉候选渠道都要能接住 `nano-banana2`：
  - 如果上游真实模型叫 `nano-banana2`，模型列表直接保留 `nano-banana2`。
  - 如果上游真实模型叫 `nano-banana-2`，渠道里要配置 `nano-banana2 -> nano-banana-2`。
- 不建议同时让画板一会儿请求 `nano-banana2`、一会儿请求 `nano-banana-2`，否则价格、日志和渠道候选都会分裂。
- 带图任务仍需单独确认 `/v1/images/edits` 兼容性；模型名统一只能解决路由候选问题，不能解决上游不支持图片编辑接口的问题。
