重要说明
============================================================
1. 这份文件只用于维护“静音中转站”，不要默认修改画板源码或封装版画板。
2. 画板面向用户的 API 地址是：https://api.jingyin.online/
   如果客户端需要 OpenAI 格式 Base URL，通常是：https://api.jingyin.online/v1
3. 服务器内部地址 127.0.0.1:8791 只给 New API 调 LK888 适配器用，画板不要填写这个地址。
4. 本文件不保存 SSH 密码、上游 API Key、用户 Token。需要时由用户临时提供，或在服务器数据库中只读确认。
5. 图片渠道不要随便点后台“测试”，有些图片渠道测试会真实扣费。优先看日志；必须真实测试时，只让用户手动画板测一张。
6. 每次改服务器文件、数据库、Nginx 配置前必须先备份。不要用 git reset、不要清空数据库、不要覆盖未知修改。

四、LK888 适配器必须保留的能力
============================================================
文件：
/opt/jingyin-lk888-gpt-image-adapter/server.py

本地模板：
D:\静音AI绘画V11（源码）\API\代码模板\lk888-gpt-image-adapter\server.py
D:\静音AI绘画V11（源码）\API\代码模板\jingyin-lk888-gpt-image-adapter.zip
D:\静音AI绘画V11（源码）\API\代码模板\jingyin-lk888-gpt-image-adapter.tar.gz

必须支持：
1. OpenAI 图片入口：
   POST /v1/images/generations
   POST /v1/images/edits
   GET /v1/models

2. 转 LK888 异步接口：
   POST https://api.lk888.ai/v1/media/generate
   GET  https://api.lk888.ai/v1/media/status?task_id=...

3. prompt 字段兼容：
   prompt
   input
   text
   message
   content
   messages
   params/body/payload/request/data 内嵌字段

4. 尺寸映射：
   画板传：
     model=gpt-image
     image_size=2K
     aspect_ratio=3:4
   LK888 适配器要转：
     model=tt-image-2
     params.size=1728x2304

   当前工作映射：
     2K + 1:1  -> 2304x2304
     2K + 3:4  -> 1728x2304
     2K + 4:3  -> 2304x1728
     2K + 9:16 -> 1296x2304
     2K + 16:9 -> 2304x1296

   注意：
   LK888 文档可能展示过另一组 2K 精确尺寸，但当前中转站实测正常的是这套从画板源码直连逻辑同步来的映射。不要没测试就随便改尺寸。

5. 尺寸容错：
   如果收到 1086x1448、1024x1536 这类中间尺寸，不要原样传给 LK888。
   应先识别比例和长边，再归一化成 LK888 可接受的尺寸或 1K/2K 标签。

6. 请求体：
   MAX_BODY_BYTES 默认 120MB。
   支持 Transfer-Encoding: chunked。
   超过上限时要先读完请求体再返回 413，避免 New API 看到 broken pipe。

7. 上传参考图压缩：
   LK888 对 params.images[0] 有单图解码后不超过 10MB 的限制。
   适配器必须在转发前把超过 9.5MB 的 multipart/base64 图片压缩成 JPEG。
   配置：
     LK888_MAX_UPSTREAM_IMAGE_BYTES=9500000
     LK888_COMPRESS_INPUT_IMAGES=true
   URL 图片不下载、不压缩，原样传给 LK888，避免中转站额外耗时。

8. 日志：
   /opt/jingyin-lk888-gpt-image-adapter/adapter.log
   可以记录：
     request_received
     upstream_request_prepared
     input_image_compressed
     upstream_size_retry
     request_failed
   不要记录：
     API Key
     SSH 密码
     完整 prompt
     图片 base64 内容


五、排障第一顺序
============================================================
遇到画板报错时，不要先改配置。按下面顺序查：

1. 问用户要：
   发生时间
   画板报错截图或文字
   用的是 GPT、香蕉、视频哪一种
   是文生图还是带参考图
   有没有手动禁用过某个渠道

2. 登录服务器后先看服务：
   systemctl is-active new-api-custom.service lk888-gpt-image-adapter.service
   ss -ltnp | grep -E ':(3001|8791|80|443) '
   curl -sS --max-time 5 http://127.0.0.1:8791/health; echo

3. 看 New API 原始日志：
   ls -lt /opt/new-api-custom/logs/oneapi-*.log | head
   grep -n -E 'POST /v1/images|channel error|relay error|do request failed|EOF|timeout|broken pipe|499|502|500' /opt/new-api-custom/logs/oneapi-最新日志.log | tail -n 200

4. 看 Nginx 请求有没有到达：
   grep 'POST /v1/images' /www/wwwlogs/api.jingyin.online.ssl.access.log | tail -n 50

5. 如果命中 LK888 channel #5：
   tail -n 120 /opt/jingyin-lk888-gpt-image-adapter/adapter.log
   重点看 request_failed.error 和 upstream_request_prepared。

6. 如果命中老夜 channel #1：
   重点看 use_time_seconds/use_time 和最终状态。
   老夜可能 200 成功但耗时 4 到 9 分钟，前端已经断开，表现为用户没收到图。

7. 查数据库消费日志，不要查 key：
   sqlite3 -header -column /opt/new-api/data/one-api.db "SELECT id,datetime(created_at,'unixepoch','localtime') AS time,channel_id,model_name,quota,use_time,request_id,substr(content,1,70) AS content FROM logs ORDER BY id DESC LIMIT 30;"

8. 查当前渠道，不要查 key：
   sqlite3 -header -column /opt/new-api/data/one-api.db "SELECT id,name,type,status,priority,weight,auto_ban,test_model,base_url,models,model_mapping,param_override,setting FROM channels ORDER BY id;"


六、常见问题和解决办法
============================================================
问题 1：前端报 lk888_adapter_error
真实含义：
前端看到的是被隐藏后的统一错误，不是真正原因。

必须查：
/opt/jingyin-lk888-gpt-image-adapter/adapter.log

可能原因和解法：
1. error=参数 size 不合法
   原因：尺寸没有归一化，或上游不收该像素。
   解法：保留/恢复尺寸白名单映射和 fallback 重试。

2. error=missing_prompt
   原因：New API 转发后 prompt 字段位置变化，适配器没读到。
   解法：保留 prompt/input/text/messages/nested 字段兼容。

3. error=字段 images[0] 文件过大
   原因：参考图解码后超过 LK888 单图 10MB。
   解法：保留 python3-pil 和输入图自动压缩到 9.5MB 以下。

4. New API 日志显示 write broken pipe 到 127.0.0.1:8791
   原因：适配器提前断开或请求体上限过小。
   解法：MAX_BODY_BYTES 保持 120MB，chunked body 必须支持，超限时先读完再返回 413。


问题 2：画板选 2K，但结果像 1K
判断：
先看请求命中哪个渠道。

如果命中 LK888：
看 adapter.log 的 upstream_request_prepared：
  image_size 是否为 2K
  aspect_ratio 是否正确
  params.size 是否为 1728x2304 / 2304x1296 等精确尺寸

如果 params.size 正确但结果仍小：
可能是 LK888 普通 tt-image-2 自身降采样，需考虑更贵的高清/官转模型，不能只靠中转站修。

如果命中老夜：
看 New API 日志 content 是否出现“大小 1728x2304”等字段，以及上游真实返回宽高。


问题 3：老夜看起来没通
已有结论：
老夜配置正常，但 GPT 图片耗时波动大。

证据：
2026-08-26 23:25:41 老夜 channel_id=1 成功 200，但耗时 418 秒。
同条记录出现 failed to copy response body: broken pipe，说明前端可能等不住断开。
2026-08-27 06:46:53 老夜 GPT 成功，用时 27 秒。

判断：
老夜不是硬故障；它是速度不稳定。

处理：
1. 不要反复改老夜 base_url、模型映射。
2. GPT 主链路优先 LK888。
3. 老夜只做兜底。
4. 如果客户没收到图但后台扣费，查是否是请求耗时太久导致前端断开。


问题 4：New API 后台没有记录，但用户说生成了
可能原因：
1. 请求还在执行，New API 通常完成后才写消费日志。
2. 前端断开后，上游稍后返回，后台再记录成功。
3. 命中了别的渠道或用户用的是直连上游，不经过静音中转站。

处理：
按 request_id 或时间查：
/opt/new-api-custom/logs/oneapi-*.log
/www/wwwlogs/api.jingyin.online.ssl.access.log
数据库 logs 表。


问题 5：渠道新增后“打架”
可能原因：
1. 多个渠道使用同一个模型名，优先级/权重导致随机或不符合预期。
2. 某个上游实际协议不同，但只做了模型名重定向，没有独立适配器。
3. New API 标准化过滤了非标准字段，导致 image_size/aspect_ratio 丢失。

处理：
1. GPT 图片走独立适配器的渠道要开启 pass_through_body_enabled=true。
2. 不同协议上游不要只靠模型名改名，必须独立适配。
3. 不要把临时测试渠道和正式渠道放到同模型同优先级。
4. 修改前先导出现有渠道快照，修改后只验证一张。


问题 6：图片下载慢或客户网络限流临时 URL
当前状态：
Nginx 已有 /jy-image-cache/ 代理到 127.0.0.1:3018。
旧缓存代理路径：/opt/jy-image-cache-proxy/proxy.py。
但 systemd 管理状态不清晰，不能把它当成完全正式功能。

后续要做成正式功能时：
1. 补 systemd 服务，确保重启服务器后自动恢复。
2. 增加开关：直连上游 URL / 缓存到中转站。
3. 设置磁盘占用超过 50% 或 70% 自动删除旧图。
4. 图片记录最多保留 7 天。
5. 保证客户收图优先，不要让缓存下载阻塞主接口返回。


七、禁止随便改的点
============================================================
1. 不要把画板 API 地址改成 127.0.0.1:8791。
2. 不要把 LK888 channel #5 的 base_url 改成 https://api.lk888.ai，它必须先走本机适配器。
3. 不要关闭 LK888 channel #5 的透传请求体。
4. 不要给 LK888 channel #5 写死 param_override 里的 size，否则画板 1K/2K/比例选择会失效。
5. 不要把 Nginx client_max_body_size 改小，必须保持至少 100m。
6. 不要把 proxy_read_timeout/proxy_send_timeout 改小，必须保持至少 600s。
7. 不要删除 python3-pil，否则 LK888 大参考图压缩会失效。
8. 不要运行旧切换脚本 /opt/jy-channel-switch/use-direct-upstream.sh，里面可能写的是旧域名 api.laoye.online，不是当前 api.luckfill.com。
9. 不要新增上游后直接放到正式最高优先级，必须先单独禁用其他同类渠道手动测试一张。
10. 不要把上游 Key 写进 TXT、Markdown、截图备注或聊天最终回复。

十、正常验证标准
============================================================
不要用后台自动测试图片渠道。

安全验证：
1. 服务健康：
   systemctl is-active new-api-custom.service lk888-gpt-image-adapter.service
   curl -sS http://127.0.0.1:8791/health

2. LK888 假 Key 格式验证：
   可以用 invalid-test-key 请求本机适配器。
   预期：adapter.log 出现 upstream_request_prepared。
   如果上游返回 API key 无效，说明格式走到上游认证阶段，不代表故障，也不会真实扣费。

3. 真实验证：
   让用户手动画板生成一张。
   不要连续点。
   生成后看 New API logs 和 adapter.log。

成功判断：
LK888 GPT：
  New API 日志 channel_id=5，状态 200。
  adapter.log 有 upstream_request_prepared。
  如果带大参考图，有 input_image_compressed 或图片本来小于 9.5MB。

老夜 GPT：
  New API 日志 channel_id=1，状态 200。
  use_time 可能波动较大；如果超过 180 秒，属于上游体验风险。

老夜香蕉：
  New API 日志 channel_id=7，模型 nano-banana2，状态 200。
