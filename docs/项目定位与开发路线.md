# 项目定位与开发路线

适用目录：`D:\RJ\静音AI绘画V5（源码）`

确认日期：2026-08-13
最后更新：2026-08-14

本文记录当前已经确认的产品定位、核心功能、业务规则边界和后续开发策略。后续开发默认遵守本文，除非有新的明确决策。

## 1. 产品定位

静音 AI 画板首先是团队内部使用的生产工具，同时也会给团队以外的人员使用。

当前最明确的目标用户是做电商设计的人群，优先服务女装电商设计场景。

这意味着它不是纯个人脚本，也不是面向大众的营销型网页，而是一个偏专业、偏生产、偏稳定交付的 AI 生图工作台。

后续设计重点：

- 功能入口要清楚，但不必做营销首页。
- 操作效率优先，适合反复生产。
- 核心链路稳定性优先于视觉花哨。
- 对外发布时要隐藏源码，保留预设提示词，不保留 KEY 和生图记录。
- 女装电商用户更关注批量稳定、版型一致、局部可控和后续进 Photoshop 修图，而不只是单张图好看。

## 2. 核心主线

当前项目核心主线是批量生成体系，尤其是：

1. 批量换装。
2. 局部回贴。
3. SKILL 和后台规则设定。
4. 快捷生成。

其中批量换装是项目核心。快捷生成是高频辅助入口，局部回贴是嵌入所有生图流程的底层能力，SKILL 和后台规则决定批量生成是否真的可用于电商生产。

详情主图目前比较稳定，后续有明确需求再优化。

图片编辑后续优化方向是更接近 Photoshop 的使用质感。当前虽然有画笔能力，但笔触丝滑度、响应、涂抹体验、撤销体验、边缘过渡都还没有达到 PS 那种顺手感。

当前批量换装最需要解决的是图2服装在多个图1模特上的一致性问题。例如袖口和袖克夫长度漂移、袖长一张到手腕一张到手掌、长袖变九分袖、宽松袖筒变正装修身、版型松量不一致、细节和面料纹理随机变化。如果这些不能稳定，批量生成就会变成“多个模特穿相似但不同款”，生产价值会明显下降。

## 4. 左侧导航策略

左侧导航目前先保持现在的显示方式。

后续如果功能继续增长，再根据真实需求调整入口。

当前不急着重做导航，也不急着把局部回贴做成单独左侧一级入口。

## 5. 局部回贴定位

局部回贴不是一个单独板块，它是嵌入到生图每个环节里的底层能力。

它的定位是：

```text
用户上传原图
-> 在原图中框选或涂抹需要变化的服装区域
-> 前端预处理局部区域
-> AI 生成局部换装结果
-> 本地程序把结果贴回原图对应位置
-> 最终保持原图场景、人物、人脸、其他元素和原始画布尺寸
```

关键原则：

- 局部回贴优先作为前端和本地后处理能力处理。
- 能预置解决的就预置解决。
- 不需要参与 SKILL 的规则，不要写进 SKILL。
- 避免 SKILL 过度参与后影响出图效果。
- 局部回贴的目标是“原位稳定”，不是让模型重新理解整张图。

## 6. 局部回贴的业务价值

局部回贴要解决的问题：

- 批量换装时人物不要偏移。
- 不改变图中场景或其他元素。
- 减少 AI 破坏人脸、头发、手、背景。
- 保留用户上传原图的高分辨率，例如原图是 8K，最终结果仍然可以是 8K。
- 方便导入 Photoshop 后，在原位擦回人脸或其它保留区域。
- 适合对服装局部做精修、换装、贴回。
- 让 AI 只负责生成局部服装变化，本地程序负责原位贴回，从而降低人物偏移和 AI 感。

这个能力是项目区别于普通 AI 生图工具的重要核心。

## 7. 三图通道定义

后续批量生成体系统一使用三图通道理解。

### 7.1 图1

图1代表批量上传图片的主上传通道。

它通常是：

- 模特图。
- 多个批量上传的模特图。
- 原始商品图。
- 需要被处理的底图。
- 局部回贴时的原图。
- 换背景、换脸、设计稿等任务里的主要处理对象。

图1是坐标、画布、原始场景和最终贴回的核心来源。

### 7.2 图2

图2是上传固定需求的通道。

它通常是：

- 固定服装需求。
- 多张服装组合图，例如上衣、裤子、鞋子。
- 固定参考对象。
- 批量换脸里的人脸身份参考。
- 固定背景参考。
- 设计稿或结构参考。

图2代表这次批量任务的主要目标需求。

在批量换装里，图2即使上传多张，也应被后台规则定义为“图2服装需求通道”，用于表达本次固定服装、套装或局部服饰组合。

在批量换脸里，图1是目标人物原图，必须保留身体、服装、姿势、背景、构图、头部坐标和光影；图2是人脸身份参考，只提供五官、脸型、年龄感、妆容气质和可融合发型方向，不迁移图2衣服、背景、拍摄角度或场景。批量姿态页才使用“图1姿态参考、图2固定母版成片”的逻辑，二者不能混用。

### 7.3 图3

图3是补充通道。

它的规则：

- 图3不是必选。
- 图3不应该在 SKILL 里默认存在。
- 图3更像临时需求补充。
- 图3只有配合用户补充提示词明确使用时才参与。
- 默认不要让图3暗中影响图1和图2的主任务。
- 图3可用于细节面料、版型补充、模特样貌、发型替换等临时需求，但必须由用户提示词明确点名。

后续任何批量工作流都要遵守：图3默认静默，除非用户提示词明确提到图3、第三张、补充图、补充参考等。

## 8. 批量工作流统一理解

批量换装、换背景、换脸、设计稿，本质上是同一个底层逻辑：

```text
图1：批量主输入
图2：固定目标需求
图3：临时补充需求
提示词：本次任务规则
前端预处理：裁剪、局部回贴、压缩、比例适配
后端 SKILL：只处理必须交给模型理解的任务规则
本地后处理：贴回、缓存、保存、下载
```

它们只是根据不同使用场景，做成针对性任务入口。

因此后续架构上不要把它们做成完全割裂的四套系统，而应该共享：

- 上传区逻辑。
- 任务队列逻辑。
- 结果卡片逻辑。
- 保存和下载逻辑。
- 局部回贴底层逻辑。
- 图1/图2/图3通道规则。

不同工作流只差：

- 默认提示词。
- 上传区文案。
- SKILL 构造方式。
- 必填图规则。
- 结果质检规则。

## 9. SKILL 边界

SKILL 只处理必须让模型理解的规则，例如：

- 这次是换装、换背景、换脸还是设计稿。
- 图1和图2分别代表什么。
- 哪些内容必须保留。
- 哪些内容要按图2或提示词生成。

以下内容尽量不要写进 SKILL：

- 普通裁剪。
- 局部回贴贴回逻辑。
- 羽化融合。
- 边缘校色。
- GPT 微对齐。
- Banana 偏色修正。
- 结果缓存。
- 自动保存。
- 下载分片。
- 图3默认存在。

原因：这些属于前端预处理或本地后处理。写进 SKILL 会让模型过度理解流程，反而可能影响出图效果。

## 10. 快捷生成定位

快捷生成是 P0 功能。

它的定位：

- 快速测试提示词。
- 快速单图生图。
- 快速参考图生图。
- 快速局部修图或局部换装。
- 给批量生成提供提示词和结果回流。

快捷生成不应该套太多批量换装规则。只有在明确触发图1局部回贴、局部换装等场景时，才使用对应保护和贴回逻辑。

## 11. 详情主图定位

详情主图目前比较稳定。

后续策略：

- 暂时不作为第一轮重构核心。
- 不主动大改。
- 等有明确业务需求后再优化。
- 可以保留现有逻辑，后续拆分时只做结构整理。

## 12. 图片编辑优化方向

图片编辑后续目标是更接近 Photoshop 的使用质感。

优化方向：

- 画笔响应更跟手。
- 鼠标/触控笔移动时笔迹更连续。
- 笔触边缘更自然。
- 撤销/重做更顺滑。
- 放大缩小时绘制坐标更稳定。
- 大图编辑不卡顿。
- 蒙版、擦除、涂抹的视觉反馈更清晰。
- 尽可能保持 PS 式工作习惯。

图片编辑是 P1，不影响当前第一轮规范化主线。

## 13. 发布交付规则

后续交付方式：

1. 先确认一个优化好的源码版本。
2. 再基于该源码版本生成二进制加密包。
3. 二进制包用于发给其他人使用。
4. 发布包保留设定好的通用提示词和每个单元的默认配置。
5. 发布包不保留 API Key。
6. 发布包不保留生图记录。
7. 发布包不保留用户运行数据。

发布前必须确认：

- `.env` 不进入发布包。
- `data` 不进入发布包。
- `logs` 不进入发布包。
- 本地历史记录不进入发布包。
- 预设提示词和默认页面配置按需要保留。

## 15. 开发方式决策

当前建议采用“稳妥小步提交 + 大改开分支”的方式。

### 15.1 小改动

文档、简单 bug、局部 UI 修正、低风险工具函数整理，可以直接在 `master` 上提交。

可以把 `master` 理解成“当前稳定主线”。它适合保存已经确认能用的版本。

### 15.2 大改动

涉及以下情况时，建议开 `codex/...` 分支：

- 拆 `src/main.jsx`。
- 拆 `src/outfit-workflow.jsx`。
- 拆 `server/index.js`。
- 调整核心出图接口。
- 调整批量换装 SKILL。
- 调整局部回贴贴回算法。
- 调整发布打包脚本。

分支命名：

```text
codex/quickgen-refactor
codex/outfit-refactor
codex/server-routes-refactor
codex/local-paste-stability
codex/release-v5
```

可以把 `codex/...` 分支理解成“试验施工区”。大改动先在分支里做，确认没破坏 P0 功能后，再决定是否合回稳定主线。这样即使中途改坏，也不会污染 `master` 上的可用版本。

建议后续执行规则：

- 小文档、小修复、小配置：直接在 `master`。
- 拆大文件、改批量生成、改局部回贴、改 SKILL、改发布包：先开 `codex/...` 分支。

### 15.3 每次修改自动 commit

后续每次 Codex 修改文件后默认提交 commit，除非用户明确要求不提交。

## 19. P0 验收清单

每次改动涉及核心链路时，至少验证：

1. 快捷生成无参考图。
2. 快捷生成带参考图。
3. 快捷生成局部回贴。
4. 批量换装。
5. 批量局部回贴。
6. 批量生成运行中继续追加任务。
7. 保存图片。
8. 下载图片。

## 20. 后续仍需确认的问题

虽然本轮已经确认了核心方向，但还有几件事需要后续单独确认：

1. 是否需要授权、试用期或设备绑定。
2. 团队外人员使用时，API Key 是自己填还是统一配置。
3. 图片编辑是否要长期做成 PS 替代型能力，还是只做轻量修图。
4. 是否需要正式素材库。
5. 是否需要历史搜索和项目分组。
7. 是否要给团队外人员准备使用说明和常见问题。
8. 是否需要默认隐藏部分高级设置，降低外部人员误操作。

## 21. 当前结论

当前最重要的不是增加更多功能，而是保护并规范三条主线：

```text
快捷生成
批量生成
局部回贴
```

后续所有开发都应该围绕这三条主线，优先保证它们稳定、清晰、可维护。

局部回贴是底层能力，不是独立页面；它应该自然嵌入到各类生图流程里，并尽量通过前端预处理和本地后处理完成，减少 SKILL 干预。

批量换装、换背景、换脸、设计稿本质是同一套批量任务框架下的不同预设工作流。后续架构要复用底层能力，不要做成互相割裂的多套系统。
