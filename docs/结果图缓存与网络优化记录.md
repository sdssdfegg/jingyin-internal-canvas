# 结果图缓存与网络优化记录

更新时间：2026-08-15

## 当前结论

最近的卡顿主因不是模型生成慢，也不是服务器内存满，而是模型返回后的结果图下载和缓存链路不稳定。

2026-08-15 紧急恢复策略：

- 暂时取消客户端默认走 `https://api.jingyin.online/v1`，源码默认回到 V1 时期老夜直连候选，先排除静音中转站对结果 URL 的影响。
- 生成成功后先把远程结果图包装成本地 `/api/image-proxy` 预览地址返回前端，后台再继续做本地缓存，避免“AI 已出图但前端一直等缓存下载”。
- `/api/image-proxy` 恢复流式转发，浏览器不必等服务端把整张远程图完整读入内存后才开始显示。
- 批量结果自动保存和手动下载增加前端 Blob 兜底：服务端保存失败时，前端再通过本地代理读取图片并提交 `/api/save-processed-image` 落盘。

当前源码侧采用本地结果缓存作为第一阶段止血方案：

- 生成结果优先缓存到 `data/results`。
- `/api/result/:filename` 从本地缓存读取结果图。
- 2026-08-15 已修正 V1 快速显示试验：不再直接暴露远程原始结果地址，而是返回本地 `/api/image-proxy` 代理预览地址；后台继续缓存到 `/api/result` 或 `/api/history-image`，自动保存另有前端 Blob 兜底。
- 缓存默认保留 7 天，超过 7 天自动清理。
- 启动时自动清理一次，运行中每 6 小时清理一次。
- 每次新结果图写入后会延迟触发一次低频清理检查，避免批量生成快速撑满磁盘。
- 当 `data/results` 所在磁盘使用率超过 80% 时，自动按旧图优先继续删除结果缓存图。
- 磁盘压力清理默认不删除 30 分钟以内刚生成的新结果，避免用户刚出的图被马上清掉。
- 浏览器对 `/api/result` 的缓存头同步为 7 天。

## 不做的事

- 不购买 CDN。
- 不改变生图提示词。
- 不改变 SKILL。
- 不改变局部回贴逻辑。
- 不改变当前结果图下载分片参数。
- 不删除自动保存到桌面的结果图。

## 后续服务器方向

如果多人同时使用后仍然卡顿，再把中转站升级为服务端结果图转存：

1. 中转站拿到上游图片地址后，先下载到自己的稳定存储。
2. 返回 `api.jingyin.online` 或 `img.jingyin.online` 下的稳定图片地址。
3. 缓存保留 7 天，超过时间自动删除。
4. 磁盘超过安全水位时自动删旧图，不让服务器靠人工清理。

长期更稳的方案是对象存储或对象存储加 CDN，但当前阶段先不上 CDN。

## 代码入口

- `server/index.js`
  - `RESULT_CACHE_TTL_DAYS`
  - `RESULT_CACHE_MAX_DISK_USAGE_RATIO`
  - `RESULT_CACHE_DISK_PRESSURE_MIN_FILE_AGE_MS`
  - `RESULT_CACHE_POST_WRITE_CLEANUP_DELAY_MS`
  - `cleanupResultCache`
  - `startResultCacheCleanup`
  - `/api/result/:filename`

## 验收点

- 启动画板不报错。
- 生成结果仍能显示和下载。
- `data/results` 中超过 7 天的图片会被自动清理。
- `data/results` 所在磁盘超过 80% 使用率时，会按旧图优先删除缓存结果图。
- 自动保存到桌面的图片不受影响。
- 日志中发生删除、磁盘压力触发或清理失败时会记录 `result-cache-cleanup`。
