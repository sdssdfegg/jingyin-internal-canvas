# 渠道策略与中转站规划

适用目录：`D:\RJ\静音AI绘画V5（源码）`

创建日期：2026-08-13

本文记录静音 AI 画板后续的渠道方向、中转站定位、价格口径和开发注意事项。后续涉及渠道、模型、KEY、价格展示、发布包时，默认参考本文。

## 1. 渠道总方向

画板后续不是直接绑定单一上游渠道，而是通过自己的中转站统一接入多个上游渠道。

当前中转站地址：

```text
https://api.jingyin.online
```

代码中接口会规范成：

```text
https://api.jingyin.online/v1
```

后续目标：

- 画板前端和客户只感知一个统一入口。
- 中转站背后可以接多个上游渠道。
- 客户不需要切换 KEY 就能调用不同上游能力。
- 同一个模型的默认渠道以老夜渠道为主。
- 价格口径默认同步老夜价格。
- 客户看到的价格不因为底层渠道变化而出现不同价位。

## 2. 主渠道定位

主渠道默认使用老夜渠道。

含义：

- 同一个模型优先走老夜渠道。
- 模型切换时默认仍以老夜渠道为主。
- 价格展示以老夜价格同步。
- 如果底层临时切换到其它备用渠道，客户侧仍保持统一价格口径。

这样做的价值：

- 客户使用简单，不需要理解多个上游。
- KEY 管理简单，不需要频繁切换。
- 价格体系统一，避免客户看到同一模型不同价格。
- 你可以在中转站内部做上游调度和兜底。

## 3. 中转站职责

中转站应该承担：

- 上游渠道统一管理。
- API Key 转发和鉴权。
- 多上游路由。
- 主渠道优先。
- 备用渠道兜底。
- 模型映射。
- 价格口径统一。
- 请求日志和用量统计。
- 失败原因追踪。
- 后续可能的客户用量、余额、限额、授权控制。

画板本地程序不应该直接暴露多个上游复杂配置给客户。

## 4. 画板本地程序职责

画板本地程序应该承担：

- UI 和工作流。
- 图片上传、裁剪、局部回贴等前端预处理。
- 本地贴回、融合、保存、历史等后处理。
- 调用统一中转站接口。
- 显示统一模型列表和统一价格口径。
- 处理接口错误和重试提示。

画板本地程序不应该承担：

- 多上游价格差异展示。
- 让客户手动选择多个底层渠道。
- 保存上游渠道密钥。
- 暴露上游真实供应商结构。

## 5. 当前代码中的渠道现状

当前后端相关文件：

```text
server/index.js
server/channel.js
src/models.js
```

当前 `server/index.js` 中已有多个锁定 baseUrl 候选，包括：

- `https://api.jingyin.online/v1`
- 其它备用渠道地址

当前 `/api/config` 返回：

```js
{
  ok: true,
  defaultBaseUrl: "https://api.jingyin.online/v1",
  fallbackBaseUrl: "",
  hasServerKey: false,
  models: CHANNEL_MODELS
}
```

当前策略已经接近“统一入口 + 备用候选”，但后续还需要进一步规范：

- 模型列表统一。
- 渠道候选配置集中。
- 价格配置集中。
- 错误和重试日志更清晰。
- 不让客户侧看到底层渠道差异。

## 6. 模型和价格策略

后续应建立统一模型配置，至少包含：

```js
{
  value: "gpt-image",
  label: "GPT2",
  ratios: ["1:1", "3:4"],
  defaultChannel: "laoye",
  priceSource: "laoye",
  visiblePrice: {},
  enabled: true
}
```

建议字段：

| 字段 | 含义 |
| --- | --- |
| `value` | 程序内部模型值 |
| `label` | UI 展示名 |
| `ratios` | 支持比例 |
| `defaultChannel` | 默认渠道，当前主方向为老夜 |
| `priceSource` | 价格口径来源，当前为老夜 |
| `visiblePrice` | 客户侧展示价格 |
| `enabled` | 是否开放 |
| `internalOnly` | 是否仅内部测试 |

注意：

- 价格配置不要散落在 UI 里。
- 同一模型底层切换渠道时，客户侧价格展示保持统一。
- 后续如果做余额或计费，应以中转站记录为准。

## 7. KEY 策略

当前确认方向：

- 客户不需要为了不同渠道切换 KEY。
- 客户侧只使用统一中转站 KEY 或你提供的统一接入方式。
- 发布包不保留 KEY。
- 源码中不写死客户 KEY。
- `.env` 不进入发布包。

后续待确认：

- 团队外人员是自己填 KEY，还是你统一发放 KEY。
- 是否需要客户授权码、试用期或设备绑定。
- 是否需要在中转站做客户级用量统计。
- 是否需要画板内显示余额或用量。

## 8. 失败和兜底策略

建议后续统一为：

```text
优先老夜渠道
-> 如果失败且符合重试条件，尝试备用渠道
-> 自动切换只记录在后台日志，不在客户界面显示底层渠道
-> 中转站后台提供“一键恢复老夜默认”
-> 客户侧仍显示同一模型和同一价格口径
-> 日志记录真实使用渠道和失败原因
```

客户端可显示：

- 余额不足。
- API Key 无效或无权限。
- 图片过大。
- 生成超时，请重新生成。
- 模型名。
- 耗时。

客户端不建议显示：

- 底层上游供应商名称。
- 不同上游的不同价格。
- 复杂渠道切换按钮。
- 备用渠道 URL、真实请求变体或上游原始报错。
- 备用尝试明细、底层模型别名、请求格式差异。

当前画板本地服务端规则：

- 每次图片请求都从主渠道开始，不缓存“上次成功备用渠道”为下一次默认。
- 老夜或当前主渠道出现超时、429、502、503、504、上游模型服务异常、模型别名/格式兼容异常时，才尝试备用渠道。
- 余额不足、API Key 无效、权限不足、图片过大这类用户或账号问题不切备用，直接给出对应业务提示。
- 如果主备都失败，前端统一显示“生成超时，请重新生成”，公开响应只保留 `requestId`、错误分类和尝试次数，真实失败链路写入 `logs/generation.jsonl`。
- 长期最优解仍是在 `api.jingyin.online` 中转站后台做模型级自动切换和“一键恢复老夜默认”，画板只作为本地保底。

当前发布口径说明：

- 默认 Win 客户端只请求静音中转站 `https://api.jingyin.online/v1`，不会在客户前端直接展示或手动切换 code28。
- `code28.ccwu.cc` 作为备用上游时，推荐接在静音中转站后台内部，由中转站完成自动 fallback、真实渠道日志和价格统一。
- “一键恢复老夜默认”目前是中转站后台待实现的运维按钮，不是画板 V6 客户端里已经存在的按钮。
- 若没有在中转站后台实现模型级 fallback，客户端日志会继续显示只请求静音中转站，画板侧也看不到“自动切到 code28”的动作。

## 9. 日志和运维

当前本地生成日志：

```text
logs/generation.jsonl
```

中转站侧后续应记录：

- 请求时间。
- 客户标识。
- 模型。
- 上游渠道。
- 消耗。
- 成功或失败。
- 错误摘要。
- 耗时。

本地发布包策略：

- 发布包不携带本地日志。
- 发布包默认不保留生图历史。
- 发布版可继续禁用或弱化生成日志，避免泄露客户数据。

运维入口：

- 中转站服务器购买和管理在云服务控制台中完成。
- 不在项目文档中记录账号、密码、Token、KEY 等敏感信息。

## 10. 后续开发任务

建议按这个顺序做渠道相关规范化：

1. 梳理当前 `server/index.js` 中渠道 baseUrl 候选逻辑。
2. 抽出 `server/config.js` 或 `server/channel-config.js`。
3. 统一 `src/models.js` 和 `server/channel.js` 的模型配置来源。
4. 增加模型价格配置结构，但先不一定显示到 UI。
5. 明确默认主渠道为老夜，备用渠道只做后台兜底。
6. 调整 `/api/config` 返回结构，为后续价格显示和渠道策略预留字段。
7. 增加日志字段：使用渠道、请求变体、失败原因、是否 fallback。
8. 在静音中转站后台新增模型级主备配置：每个模型默认老夜主渠道，失败时按错误类型自动尝试 code28 或其它备用上游。
9. 在静音中转站后台新增“一键恢复老夜默认”：把所有模型的默认上游恢复为老夜，并清除临时故障切换状态。
10. 在静音中转站后台新增 fallback 日志面板：记录请求 ID、模型、主渠道失败原因、备用渠道是否接管、耗时、实际消耗和对客户展示的包装错误。
11. 画板客户端后续只做内部诊断入口，不给客户显示备用渠道名称、备用价格、真实上游错误和手动渠道按钮。
12. 后续如需要，再接客户用量、余额、授权。

## 11. 改动红线

- 不要把上游 KEY 写进源码。
- 不要把客户 KEY 写进发布包。
- 不要让客户必须理解多个上游渠道。
- 不要在 UI 上暴露多个渠道价格差异。
- 不要让同一个模型因为底层渠道变化显示不同价位。
- 不要把云服务控制台账号、密码、Token 写进仓库。

## 12. 当前结论

渠道架构目标是：

```text
画板客户端
-> 静音中转站 https://api.jingyin.online 做 KEY 校验、余额扣费、消费记录、模型映射和任务签发
-> 老夜 / 新 IMAGE2 / 兰兰达等真实上游承接图片与视频大流量
-> 必要时后台 fallback 到其它上游
-> 客户侧保持统一 KEY、统一模型、统一价格口径
```

这个方向适合后续对团队外人员交付，因为客户使用简单，你也能在后台灵活调整上游渠道，同时避免 `api.jingyin.online` 因为代理大图、大视频上传下载而成为卡点。

## 13. 2026-08-14 慢速排查结论

- 本轮日志显示，生成突然超过 3 分钟的主因不是分片下载，也不是把图片下载到静音中转站，而是失败后的请求变体和渠道候选重试被放大：一次 524/openai_error 会等待约 128 秒，随后继续尝试 pixel、legacy、openai 兼容格式，累计达到 3-6 分钟。
- 画板客户端默认只调用 `https://api.jingyin.online/v1`。老夜、code28 等上游切换应该放在静音中转站内部处理，客户侧始终只看到统一模型、统一 KEY 和老夜价格口径。
- 本地直连备用渠道默认关闭；仅在内部排障时显式设置 `JINGYIN_ENABLE_CLIENT_CHANNEL_FALLBACKS=1` 才启用。
- `gpt-image-1` OpenAI 兼容变体默认关闭；仅在显式设置 `JINGYIN_ENABLE_OPENAI_IMAGE_VARIANT=1` 时启用。
- 请求变体只在参数格式或模型别名不兼容时重试；429、502、503、504、524、timeout、openai_error、upstream 这类渠道/上游问题不再继续换格式重试，前端统一显示“生成超时，请重新生成”，真实原因写入后台日志。

## 14. 2026-08-16 新 IMAGE2 通道接入边界

本轮新增 `jingyin.kk0606.com` 体系的 IMAGE2 图片通道，代码实际请求 Base URL 为 `https://api.lk888.ai/v1`，前端仍保持统一显示 `GPT2` / `gpt-image`。服务端会在图片生成时把 `gpt-image` 映射为新站真实模型 `gpt-image-2`，只影响 `/images/generations` 和 `/images/edits` 这类图片生成请求。

当前短期策略：
- `GPT2 / gpt-image` 图片生成默认先走新站 IMAGE2 通道。
- 新站失败且属于渠道故障、超时、上游异常、限流等可兜底错误时，再尝试老夜直连候选。
- 余额不足、KEY 错误、权限不足、图片过大等账号/参数类问题不切备用，直接返回对应业务提示。
- 客户端不显示新站名称、底层价格、真实上游错误和备用尝试明细，只显示统一模型与包装后的错误。

双 KEY 说明：
- 客户在画板里填写的 KEY 不随底层渠道变化，仍作为静音画板统一入口、客户识别和价格口径使用。
- 新站 IMAGE2 首选通道需要服务端私密上游 KEY，配置在本机 `.env` 或服务器环境变量 `JINGYIN_IMAGE2_PRIMARY_API_KEY`。
- 服务端发往 `https://api.lk888.ai/v1` 时使用该私密上游 KEY；回退到老夜等旧候选时仍使用客户运行时 KEY。
- 如果没有配置 `JINGYIN_IMAGE2_PRIMARY_API_KEY`，画板不会拿客户 KEY 去试新站 IMAGE2，而是跳过该隐藏首选通道，继续使用后续老夜候选。
- 私密上游 KEY 不写入源码、文档、提交、日志或发布包；日志只记录是否配置了渠道 KEY 和是否使用私密渠道 KEY。

价格优先说明：
- 本次接口文档没有发现需要随请求传入的“价格优先”字段；它更像是新站后台/渠道组策略。
- 文档明确提示价格优先渠道可能降采样，`size` 更稳定地决定比例，不保证真实输出像素完全等于请求像素。
- 画板代码只负责把请求发到该新站 IMAGE2 通道，并使用 OpenAI 兼容的 `size` 参数；是否价格优先由新站后台渠道策略决定。

长期目标：
- `api.jingyin.online` 仍应作为统一 KEY、统一加价、统一用量和客户价格展示入口。
- 但大图上传、模型返回图片和下载链路不要再完整穿过旧服务器代理，否则旧服务器带宽、内存和大文件中转会继续成为卡点。
- 更合适的方式是：旧中转站只做鉴权、计费、模型映射和路由签发；图片重流量由新站或对象存储/CDN 承接。
- 任何上游 KEY、后台账号、测试密钥都不得写入源码、文档、日志提交和发布包。

## 16. 2026-08-16 统一轻量计费网关原则

后续所有外接中转 API，包括老夜、新 IMAGE2、兰兰达视频、code28 或其它备用渠道，都统一遵循“计费与大文件处理分离”的架构。

目标链路：

```text
画板
-> api.jingyin.online：客户 KEY 校验、余额检查、预扣/扣费、消费记录、模型映射、任务签发
-> 真实上游：老夜 / 新 IMAGE2 / 兰兰达等负责实际图片或视频生成
-> 画板或对象存储/CDN：承接源文件上传、结果图/视频下载、缓存和预览
```

核心原则：

- `api.jingyin.online` 是统一价格和计费入口，不再作为图片/视频大流量代理。
- 老夜渠道也要改成同样模式：中转站只做计费签发，真实生图由老夜通道承接。
- 新 IMAGE2 和兰兰达视频沿用同一套签发逻辑，避免每个渠道单独发明一套计费方式。
- 客户侧始终只看到静音统一 KEY、统一模型名、统一售价和包装后的错误提示。
- 后台日志必须能查到真实上游、请求 ID、上游任务 ID、扣费状态、fallback 状态和耗时阶段。
- 上游成本价只作为内部核算，客户销售价在 `api.jingyin.online` 后台按模型、尺寸、分辨率、时长或倍率单独设置。

这条原则优先级高于具体渠道实现。后续新增任何外接 API 时，默认先判断它能否走“轻量计费签发 + 上游处理大文件”，不要再默认把源文件和结果文件完整压到旧中转站。

## 17. 2026-08-16 源码侧轻量计费适配层

源码已新增 `server/billing-gateway.js`，用于把图片、批量换装和视频生成统一接到“轻量计费签发”流程。

当前接入点：

- `/api/images`：快捷生成、图片编辑等通用图片生成入口。
- `/api/generate-outfit`：批量换装、批量换脸、批量换背景等批量工作流的真实生图入口。
- `/api/videos/generations`：兰兰达 Seedance 视频创建任务入口。

运行方式：

- 默认 `JINGYIN_BILLING_GATEWAY_ENABLED=0`，不影响当前源码直连上游出图。
- 等 `api.jingyin.online` 后端准备好轻量接口后，再设置 `JINGYIN_BILLING_GATEWAY_ENABLED=1`。
- 默认签发接口为 `POST /api/gateway/tasks/prepare`，默认结算接口为 `POST /api/gateway/tasks/finalize`，如后端路径不同可用环境变量覆盖。
- prepare 只发送客户 KEY、显示模型、尺寸、数量、任务类型、候选渠道 ID、文件数量和总字节数等轻量 JSON，不上传原图和结果图。
- finalize 只回写成功/失败、使用渠道、真实模型、上游任务 ID、输出数量、耗时和简化后的尝试记录，不让旧服务器承接大文件流量。
- 2026-08-17 源码侧已补齐图片签发路由执行：图片 prepare 如果返回 `route` 或 `upstream`，`/api/images` 和 `/api/generate-outfit` 会优先使用该路由直连真实图片上游；签发路由失败才回退本机原有候选。
- 当前用假 KEY 探测 `https://api.jingyin.online/api/gateway/tasks/prepare` 返回 `404`，说明旧中转站轻量接口尚未上线；接口上线前不要默认打开 `JINGYIN_BILLING_GATEWAY_ENABLED=1`，避免客户机器生成失败。

图片签发路由：

- 图片 prepare 的 `usage` 会带上 `kind: "image"`、显示模型、尺寸、比例、数量、文件数量和上传总字节数。
- prepare 可返回 `route` 或 `upstream` 对象，源码会优先使用其中的 `baseUrl`、`generationUrl` / `editUrl` / `createUrl`、`headers`、`apiKey`、`model`、`channelId` 和 `channelRole` 创建图片任务。
- 如果图片签发路由没有返回，或计费网关未启用，源码保持现有候选顺序：新 IMAGE2 私密通道可用时优先新站，否则继续老夜直连候选。

兰兰达视频签发路由：

- 视频 prepare 的 `usage` 会带上 `billingSku`，格式为 `video:{model}:{resolution}:{duration}s`，例如 `video:seedance-2.0:720p:5s`。`api.jingyin.online` 后台可按这个 SKU 或按 `model + resolution + duration` 设置客户售价。
- prepare 可返回 `route` 或 `upstream` 对象，源码会优先使用该对象里的 LANLANDA 上游地址和授权信息创建任务；如果没有签发路由，源码才退回本机 `JINGYIN_LANLANDA_VIDEO_API_KEY`。
- 签发路由示例字段：`baseUrl`、`createUrl`、`statusUrlTemplate`、`headers`、`apiKey`、`channelId`、`channelRole`。真实 KEY 只能由服务端在运行时返回或写入服务器环境变量，不写进源码和文档。
- 视频创建成功后，源码会在本机内存里保存短期路由会话，默认 4 小时，用于 `GET /v1/video/generations/{task_id}` 状态轮询；中转站不需要代理视频结果文件。
- 前端视频入口以“静音计费网关可签发”作为可用条件之一，不再要求客户机本地保存兰兰达真实 KEY；这保证价格、KEY、记录仍由 `api.jingyin.online` 统一控制，同时大视频链路走上游。

老夜渠道拆分：

- `server/channel-config.js` 已给老夜主/备直连端点预留 `JINGYIN_LAOYE_PRIMARY_API_KEY`、`JINGYIN_LAOYE_SECONDARY_API_KEY`。
- 正式环境配置这两个私密上游 KEY 后，画板里的客户 KEY 只负责进入 `api.jingyin.online` 做校验、扣费和记录；真实老夜生图请求使用服务端私密 KEY。
- 如果这两个 KEY 未配置，源码仍会按当前兼容方式使用运行时客户 KEY 请求老夜，保证测试环境不突然断图。

正式上线红线：

- 不要在 `api.jingyin.online` 轻量接口未上线前打开 `JINGYIN_BILLING_GATEWAY_ENABLED=1`。
- 不要把老夜、新 IMAGE2、兰兰达等真实上游 KEY 写进源码、文档、日志或发布包。
- 不要让客户 UI 展示真实上游渠道名、真实上游价格、备用切换过程和上游原始错误。
