# 本地源码网页版部署与任务隔离方案

适用目录：`D:\RJ\静音AI绘画V5（源码）`

编写日期：2026-08-13

目标：把当前本地运行的静音 AI 绘画 V5 源码，改造成可多人在线使用的网页版。网页版前端静态资源走 CDN 网络分发，后端负责登录、用户隔离、任务队列、并发锁、出图归属、结果存储和任务 ID 明细，确保“谁用的是谁的，谁出的图是谁的”。

## 1. 先说结论

当前项目已经具备网页版基础：

- 前端是 `Vite + React`，可以直接构建成静态资源。
- 后端是 `Node.js + Express`，已经把 AI Key、图片转发、历史记录、保存、结果缓存放在服务端。
- 出图接口已经集中在 `/api/images` 和 `/api/generate-outfit`。
- 当前已经有任务 ID 雏形：快捷生成返回 `requestId`，批量换装返回 `taskId`。

但当前仍是“单机本地画板”架构，不适合直接多人上线：

- 登录体系缺失，接口不知道当前是谁在用。
- 历史记录写到本地 `data/history.json`，多人会混在一起。
- 结果图写到本地 `data/results`、`data/history-images`，没有用户隔离。
- API Key 现在主要由前端传入，网页版不能让用户之间串 Key。
- `server/index.js` 里的 `acquireImageSlot()` 目前全部放行，只统计活跃请求，没有真正的并发锁。
- 本地保存目录、打开目录、选择目录这些桌面能力，网页版不能照搬。

因此网页版改造的核心不是“把页面放到服务器上”这么简单，而是补齐 6 个系统能力：

1. 用户登录和身份识别。
2. 任务 ID 和任务状态表。
3. 用户级、账号级、渠道级并发锁。
4. 图片结果按用户归属存储。
5. 前端静态资源 CDN 分发。
6. 后端 API、任务队列、数据库、对象存储拆分部署。

## 2. 当前源码和网页版目标对照

| 当前本地能力 | 当前实现 | 网页版目标 |
| --- | --- | --- |
| 前端页面 | `src` + Vite，开发时由 Express 挂 Vite 中间件 | `npm run build` 后上传 CDN |
| 后端接口 | `server/index.js` 单体 Express | API 服务独立部署，多实例可横向扩容 |
| 出图接口 | `/api/images`、`/api/generate-outfit` | 接口只创建任务或同步短任务，任务全量入库 |
| 历史记录 | `data/history.json` | 数据库按 `user_id` 查询 |
| 历史图片 | `data/history-images` | 对象存储按用户目录隔离 |
| 批量结果缓存 | `data/results` | 对象存储 + CDN 私有访问或签名 URL |
| 保存目录 | `data/app-settings.json` 和本地目录 | 云端素材库、用户下载、批量打包下载 |
| API Key | 前端传入或服务端环境变量 | 用户 Key 加密存储，或平台统一 Key 池 |
| 并发控制 | `acquireImageSlot()` 当前全部放行 | Redis 分布式锁 + 任务队列限流 |
| 日志 | `logs/generation.jsonl` | 数据库任务日志 + 文件日志 + 监控告警 |

## 3. 目标网页版架构

```text
用户浏览器
  |
  | 访问 https://www.jingyinai.com
  v
CDN
  |
  | 分发 index.html、JS、CSS、图标等静态资源
  v
前端 React SPA
  |
  | HTTPS /api/*
  v
API 网关 / Nginx / 负载均衡
  |
  v
Node.js API 服务
  |
  | 创建任务、鉴权、查数据库、发队列
  v
Redis + 任务队列
  |
  | Worker 获取任务、加并发锁、调用渠道
  v
AI 渠道接口
  |
  | 返回图片 URL 或 base64
  v
对象存储 OSS/COS/S3/R2
  |
  | 保存用户上传图、生成图、结果图
  v
数据库 PostgreSQL/MySQL
  |
  | 保存用户、任务、图片、计费、日志
  v
前端按 taskId 查询任务和结果
```

建议部署拆成四层：

- CDN 层：只放前端静态资源。
- API 层：Express 服务，负责鉴权、参数校验、任务创建、结果查询。
- Worker 层：真正执行出图任务，负责调用 AI 渠道、保存结果、释放锁。
- 数据层：数据库、Redis、对象存储。

## 4. CDN 网络分发方案

### 4.1 CDN 分发什么

CDN 只分发前端静态文件，不直接跑 Node 后端。

需要上传 CDN 或对象存储的文件来自：

```text
D:\RJ\静音AI绘画V5（源码）\dist
```

构建命令：

```powershell
cd D:\RJ\静音AI绘画V5（源码）
npm run build
```

构建后一般会产生：

```text
dist/index.html
dist/assets/*.js
dist/assets/*.css
dist/*.ico
dist/*.webp
```

### 4.2 CDN 域名建议

建议拆两个域名：

```text
https://www.jingyinai.com       前端页面，走 CDN
https://api.jingyinai.com       后端 API，不走静态 CDN 缓存
https://cdn.jingyinai.com       图片资源 CDN，可用于公开或签名图片
```

如果先做内测，也可以：

```text
https://web.jingyinai.com
https://api.jingyinai.com
```

### 4.3 前端 API 地址改造

当前前端 API 基本使用相对路径：

```js
fetch("/api/images")
```

本地运行时这很好，因为页面和 API 都在 `127.0.0.1:8787`。

网页版 CDN 场景下，页面来自 `www.jingyinai.com`，API 来自 `api.jingyinai.com`，需要支持环境变量：

```text
VITE_API_BASE_URL=https://api.jingyinai.com
```

建议改造 `src/api/client.js`：

```js
const API_BASE_URL = import.meta.env.VITE_API_BASE_URL || "";

export async function apiJson(url, options = {}, fallbackMessage = "请求失败") {
  const targetUrl = url.startsWith("http") ? url : `${API_BASE_URL}${url}`;
  const response = await fetch(targetUrl, {
    ...options,
    credentials: "include",
    headers: {
      ...(options.body instanceof FormData ? {} : { "Content-Type": "application/json" }),
      ...(options.headers || {})
    }
  });
  const payload = await response.json().catch(() => null);
  if (!response.ok || payload?.ok === false) {
    throw new Error(payload?.message || fallbackMessage);
  }
  return payload || {};
}
```

要点：

- `credentials: "include"` 用于携带登录 Cookie。
- 不要在每个组件里拼 API 域名，只在 `src/api/client.js` 统一处理。
- 本地开发可以继续用空 `VITE_API_BASE_URL`，保持 `/api/...` 相对路径。

### 4.4 CDN 缓存规则

建议缓存规则：

| 文件 | 缓存策略 |
| --- | --- |
| `/index.html` | 不强缓存，`Cache-Control: no-cache` |
| `/assets/*.js` | 强缓存 1 年，`max-age=31536000, immutable` |
| `/assets/*.css` | 强缓存 1 年，`max-age=31536000, immutable` |
| 图标、字体、公开图片 | 强缓存 1 年 |
| 用户生成图片 | 默认私有，不直接公开缓存；需要展示时用签名 URL |

原因：

- Vite 构建出来的 JS/CSS 文件名带 hash，适合长期缓存。
- `index.html` 不能长期缓存，否则新版本发布后用户可能一直加载旧入口。
- 用户图片涉及归属和隐私，不建议默认公开。

### 4.5 CDN 发布步骤

第一版发布流程：

1. 在服务器或本机执行：

```powershell
cd D:\RJ\静音AI绘画V5（源码）
npm install
npm run build
```

2. 将 `dist` 目录上传到对象存储静态站点桶。
3. 给对象存储绑定 CDN 域名，例如 `www.jingyinai.com`。
4. CDN 设置 HTTPS 证书。
5. CDN 设置 SPA 回源规则：找不到路径时返回 `/index.html`。
6. 设置 `index.html` 不强缓存。
7. 设置 `assets` 目录强缓存。
8. 前端构建时注入：

```text
VITE_API_BASE_URL=https://api.jingyinai.com
```

9. 验证：

```text
https://www.jingyinai.com
https://www.jingyinai.com/assets/xxx.js
https://api.jingyinai.com/api/config
```

### 4.6 CDN 回滚步骤

每次发布都保留一个版本目录：

```text
releases/web/2026-08-13-001/
releases/web/2026-08-13-002/
```

CDN 当前版本指向：

```text
current -> releases/web/2026-08-13-002/
```

回滚时只切换 `current` 指向上一版，并刷新 CDN 的 `/index.html`。

## 5. 后端部署改造

### 5.1 监听地址

当前服务启动在：

```js
app.listen(PORT, "127.0.0.1")
```

本地桌面软件这样是对的，但服务器部署需要让 Nginx 或负载均衡访问。

建议改成环境变量控制：

```js
const HOST = process.env.HOST || "127.0.0.1";
app.listen(PORT, HOST, () => {
  console.log(`Jingyin API http://${HOST}:${PORT}`);
});
```

服务器内网部署：

```text
HOST=0.0.0.0
PORT=8787
```

如果前面有 Nginx，同一台机器上也可以继续监听 `127.0.0.1`，由 Nginx 反代。

### 5.2 Nginx 反向代理

示例：

```nginx
server {
  listen 443 ssl http2;
  server_name api.jingyinai.com;

  client_max_body_size 80m;
  proxy_read_timeout 1000s;
  proxy_send_timeout 1000s;

  location /api/ {
    proxy_pass http://127.0.0.1:8787;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }
}
```

注意：

- 图片生成耗时可能很长，`proxy_read_timeout` 必须放大。
- 上传图片较大，`client_max_body_size` 不能太小。
- API 域名不要开启普通静态 CDN 缓存。

### 5.3 后端环境变量

建议增加：

```text
NODE_ENV=production
HOST=127.0.0.1
PORT=8787
PUBLIC_WEB_ORIGIN=https://www.jingyinai.com
DATABASE_URL=postgres://...
REDIS_URL=redis://...
OBJECT_STORAGE_BUCKET=jingyin-ai-prod
OBJECT_STORAGE_PUBLIC_BASE=https://cdn.jingyinai.com
TASK_QUEUE_CONCURRENCY=4
USER_DEFAULT_CONCURRENCY=1
CHANNEL_GLOBAL_CONCURRENCY=8
IMAGE_REQUEST_TIMEOUT_MS=900000
LOCAL_HTTP_TIMEOUT_MS=960000
```

### 5.4 CORS 和 Cookie

如果前端和 API 分域：

```text
www.jingyinai.com
api.jingyinai.com
```

后端要允许前端来源：

```js
app.use(cors({
  origin: process.env.PUBLIC_WEB_ORIGIN,
  credentials: true
}));
```

登录 Cookie 建议：

```text
HttpOnly
Secure
SameSite=None
Domain=.jingyinai.com
```

如果不使用 Cookie，也可以使用 Bearer Token。但图片上传和普通浏览器使用场景里，HttpOnly Cookie 更不容易被前端脚本读走。

## 6. 登录、用户隔离和“谁用的是谁的”

### 6.1 必须有登录态

所有出图、历史、素材、保存、任务查询接口都必须知道当前用户：

```js
const user = await requireAuth(req);
```

没有登录的请求不能调用：

- `/api/images`
- `/api/generate-outfit`
- `/api/history`
- `/api/save-image`
- `/api/save-processed-image`
- `/api/canvas-assets`
- `/api/outfit-master-fit-analysis`
- `/api/outfit-quality-check`

可以匿名访问的接口只保留：

- `GET /api/config`，并且只返回公开配置。
- 登录、注册、验证码等认证接口。

### 6.2 用户 ID 是归属根

所有核心数据必须带 `user_id`：

```text
users.id
generation_tasks.user_id
task_images.user_id
user_assets.user_id
user_api_keys.user_id
credit_ledger.user_id
```

任何查询都必须加：

```sql
WHERE user_id = 当前登录用户
```

不要只靠前端传 `taskId` 查询，因为别人拿到 taskId 可能越权访问。

### 6.3 接口里的归属规则

创建任务时：

```text
登录用户 user_id
-> 服务端生成 task_id
-> task.user_id = user_id
-> 上传图 object_key 前缀带 user_id/task_id
-> 生成图 object_key 前缀带 user_id/task_id
-> 返回给前端的任务只包含当前用户可见信息
```

查询任务时：

```sql
SELECT * FROM generation_tasks
WHERE task_id = $1 AND user_id = $2
```

删除任务时：

```sql
UPDATE generation_tasks
SET deleted_at = now()
WHERE task_id = $1 AND user_id = $2
```

下载图片时：

```sql
SELECT * FROM task_images
WHERE image_id = $1 AND user_id = $2
```

只要所有读写都带 `user_id`，就能实现“谁出的图是谁的”。

## 7. 任务 ID 明细设计

### 7.1 任务 ID 的作用

任务 ID 不是简单前端临时 ID，它必须贯穿整个链路：

```text
前端创建任务
-> 后端入库
-> Redis 队列
-> Worker 调 AI 渠道
-> 日志记录
-> 图片对象存储
-> 前端查询状态
-> 用户下载结果
-> 客服排查问题
```

以后排查任何问题，第一句话应该能问：

```text
这个任务 ID 是多少？
```

### 7.2 任务 ID 格式

建议统一格式：

```text
jy_业务类型_日期_随机串
```

示例：

```text
jy_img_20260813_01J4Q8M2K6P9B7C3D5E6F7G8H9
jy_outfit_20260813_01J4Q8N0Z1A2B3C4D5E6F7G8J0
jy_detail_20260813_01J4Q8PA3B4C5D6E7F8G9H0J1
jy_resize_20260813_01J4Q8QB5C6D7E8F9G0H1J2K3
```

推荐随机串使用 ULID，因为它大致按时间排序，排查日志方便。

业务类型建议：

| 前缀 | 业务 |
| --- | --- |
| `jy_img` | 快捷生成、通用 `/api/images` |
| `jy_outfit` | 批量换装、局部回贴、换背景、换脸、姿态 |
| `jy_detail` | 一键详情主图 |
| `jy_reference` | 参考生图 |
| `jy_resize` | 批量改尺寸 |
| `jy_editor` | 图片编辑导出 |

### 7.3 子任务 ID

批量任务里会有多张图、多次生成，需要子任务：

```text
主任务 task_id:
jy_outfit_20260813_01J4Q8N0Z1A2B3C4D5E6F7G8J0

子任务 subtask_id:
jy_outfit_20260813_01J4Q8N0Z1A2B3C4D5E6F7G8J0_001
jy_outfit_20260813_01J4Q8N0Z1A2B3C4D5E6F7G8J0_002
jy_outfit_20260813_01J4Q8N0Z1A2B3C4D5E6F7G8J0_003
```

每个子任务记录：

- 使用哪张图 1。
- 使用哪张图 2。
- 是否使用图 3。
- 工作流模式。
- 提示词。
- 渠道模型。
- 状态。
- 输出图片。
- 错误信息。
- 耗时。

### 7.4 图片 ID

每一张上传图和生成图也要有 ID：

```text
img_in_20260813_01J4Q8...
img_out_20260813_01J4Q9...
```

图片表要能回答：

- 这张图是谁上传的？
- 属于哪个任务？
- 是输入图还是输出图？
- 对应对象存储路径是什么？
- 是否允许 CDN 签名访问？
- 是否已删除？

## 8. 任务状态设计

任务主状态建议：

| 状态 | 含义 |
| --- | --- |
| `created` | 已创建，参数已入库 |
| `queued` | 已进入队列，等待执行 |
| `locked` | 已拿到并发锁，准备调用渠道 |
| `running` | 正在调用 AI 渠道 |
| `saving` | 渠道已返回，正在保存图片 |
| `succeeded` | 成功 |
| `failed` | 失败 |
| `cancelled` | 用户取消 |
| `timeout` | 超时 |

前端展示可以简化为：

```text
排队中
生成中
保存中
已完成
失败
已取消
```

数据库保留更细状态，方便排查。

## 9. 数据库表设计

建议使用 PostgreSQL。如果团队更熟 MySQL，也可以用 MySQL，字段设计类似。

### 9.1 用户表 `users`

```sql
CREATE TABLE users (
  id UUID PRIMARY KEY,
  phone VARCHAR(32),
  email VARCHAR(255),
  nickname VARCHAR(100),
  password_hash TEXT,
  status VARCHAR(32) NOT NULL DEFAULT 'active',
  plan VARCHAR(32) NOT NULL DEFAULT 'free',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);
```

### 9.2 用户 API Key 表 `user_api_keys`

如果是用户自己填 Key：

```sql
CREATE TABLE user_api_keys (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL REFERENCES users(id),
  provider VARCHAR(64) NOT NULL,
  key_ciphertext TEXT NOT NULL,
  key_hash VARCHAR(128) NOT NULL,
  status VARCHAR(32) NOT NULL DEFAULT 'active',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_user_api_keys_user ON user_api_keys(user_id);
```

注意：

- 数据库不保存明文 Key。
- `key_ciphertext` 用服务端密钥加密。
- `key_hash` 用来判断重复和做缓存，不能还原 Key。

如果是平台统一 Key 池，则增加 `platform_api_keys` 表，按渠道和额度调度。

### 9.3 任务表 `generation_tasks`

```sql
CREATE TABLE generation_tasks (
  id UUID PRIMARY KEY,
  task_id VARCHAR(96) NOT NULL UNIQUE,
  parent_task_id VARCHAR(96),
  user_id UUID NOT NULL REFERENCES users(id),
  source VARCHAR(64) NOT NULL,
  workflow_mode VARCHAR(64),
  status VARCHAR(32) NOT NULL,
  queue_name VARCHAR(64),
  model VARCHAR(128),
  image_size VARCHAR(32),
  aspect_ratio VARCHAR(32),
  prompt TEXT,
  prompt_hash VARCHAR(128),
  params_json JSONB NOT NULL DEFAULT '{}',
  input_json JSONB NOT NULL DEFAULT '{}',
  result_json JSONB NOT NULL DEFAULT '{}',
  error_code VARCHAR(128),
  error_message TEXT,
  attempt_count INT NOT NULL DEFAULT 0,
  queue_position INT,
  lock_key VARCHAR(255),
  lock_owner VARCHAR(128),
  timing_json JSONB NOT NULL DEFAULT '{}',
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  queued_at TIMESTAMPTZ,
  started_at TIMESTAMPTZ,
  finished_at TIMESTAMPTZ,
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  deleted_at TIMESTAMPTZ
);

CREATE INDEX idx_generation_tasks_user_created ON generation_tasks(user_id, created_at DESC);
CREATE INDEX idx_generation_tasks_status ON generation_tasks(status);
CREATE INDEX idx_generation_tasks_parent ON generation_tasks(parent_task_id);
```

字段说明：

- `task_id`：对外展示和排查使用的任务 ID。
- `parent_task_id`：批量任务主任务和子任务关联。
- `user_id`：归属，所有查询必须带它。
- `source`：快捷生成、批量、详情、参考、编辑等来源。
- `workflow_mode`：批量换装、局部回贴、换背景、换脸等。
- `params_json`：模型、比例、生成数量、页面名、上传标签等参数。
- `input_json`：输入图片 ID、输入文件信息。
- `result_json`：渠道响应摘要、输出图片 ID、最终 URL。
- `lock_key`：本任务拿到的锁。
- `lock_owner`：执行该任务的 worker 实例。
- `timing_json`：排队耗时、渠道耗时、保存耗时、总耗时。

### 9.4 图片表 `task_images`

```sql
CREATE TABLE task_images (
  id UUID PRIMARY KEY,
  image_id VARCHAR(96) NOT NULL UNIQUE,
```

## 11. 并发锁设计

### 11.1 为什么必须做并发锁

网页版多人同时使用时，会出现这些问题：

- 一个用户连续点很多次生成，把服务器和渠道打满。
- 多个用户同时使用同一个渠道 Key，触发限流。
- 批量任务一次几十张图，挤掉别人的快捷生成。
- 某个 Worker 崩溃，锁不释放，任务永远卡住。
- 没有任务归属时，任务返回结果可能被错误写到全局历史。

所以并发锁必须同时管 4 件事：

1. 用户并发：每个用户最多同时跑几个任务。
2. 渠道并发：每个渠道或 Key 最多同时跑几个任务。
3. 全局并发：整个平台最多同时跑几个任务。
4. 批量任务公平性：一个批量任务不能一次占满所有执行槽。

### 11.2 当前代码需要替换的位置

当前 `server/index.js` 里有：

```js
const IMAGE_CONCURRENCY_LIMIT = Number.POSITIVE_INFINITY;
let activeImageRequestCount = 0;
const imageRequestQueue = [];

function acquireImageSlot(weight = 1) {
  const slotWeight = imageSlotWeight(weight);
  activeImageRequestCount += slotWeight;
  let released = false;
  return Promise.resolve(() => {
    if (released) return;
    released = true;
    activeImageRequestCount = Math.max(0, activeImageRequestCount - slotWeight);
    queueMicrotask(drainImageQueue);
  });
}
```

本地版这样可以减少排队，但网页版必须改为 Redis 分布式锁。原因是上线后后端可能有多个 Node 进程或多个服务器，内存变量只能管当前进程，管不住全局。

### 11.3 Redis 锁 key

建议锁 key：

```text
lock:global:image
lock:user:{user_id}:image
lock:channel:{channel_id}:image
lock:apikey:{api_key_hash}:image
lock:task:{task_id}
```

含义：

| 锁 | 作用 |
| --- | --- |
| `lock:global:image` | 限制整个平台同时出图数量 |
| `lock:user:{user_id}:image` | 限制单个用户同时出图数量 |
| `lock:channel:{channel_id}:image` | 限制某个渠道整体并发 |
| `lock:apikey:{api_key_hash}:image` | 限制同一把 Key 同时请求数量 |
| `lock:task:{task_id}` | 防止同一个任务被重复执行 |

### 11.4 推荐并发限制

内测第一版建议：

| 类型 | 免费用户 | 付费用户 | 管理员 |
| --- | --- | --- | --- |
| 单用户同时出图 | 1 | 2-4 | 4-8 |
| 单用户排队任务 | 10 | 50 | 200 |
| 平台全局同时出图 | 按服务器和渠道能力设置，例如 4-20 | 按服务器和渠道能力设置 | 按服务器和渠道能力设置 |
| 单 Key 同时出图 | 1-2 | 1-4 | 视渠道限制 |

批量生成建议：

- 一个批量主任务可以包含很多子任务。
- 子任务进入队列，但每个用户最多同时执行 1-2 个子任务。
- 这样不会因为一个人的批量任务把所有执行槽占满。

### 11.5 并发锁流程

```text
用户提交生成
-> API 创建 task_id
-> 写 generation_tasks(status=created)
-> 检查用户排队任务数量
-> 扣除或预冻结额度
-> 写 queued 状态
-> 投递 Redis 队列
-> Worker 获取任务
-> 获取 task 锁，防止重复执行
-> 获取 user 锁
-> 获取 apiKey/channel 锁
-> 获取 global 锁
-> 全部成功后 status=running
-> 调 AI 渠道
-> 保存图片到对象存储
-> 写 task_images
-> status=succeeded
-> 释放所有锁
```

失败时：

```text
任一环节失败
-> status=failed 或 timeout
-> 写 error_code 和 error_message
-> 释放已拿到的锁
-> 退还冻结额度，或记录失败不扣费
```

### 11.6 锁 TTL

所有锁必须带过期时间，防止 Worker 崩溃后永久占锁。

建议：

```text
普通快捷生成锁 TTL：20 分钟
批量单张子任务锁 TTL：20 分钟
详情主图单张锁 TTL：20 分钟
任务执行锁 TTL：30 分钟
```

Worker 执行中可以定时续期：

```text
每 30 秒续期一次
```

如果 Worker 崩溃：

- 锁自动过期。
- 队列任务可重试。
- 数据库里长时间 `running` 的任务由定时任务扫描改成 `timeout` 或重新入队。

### 11.7 Redis 信号量示例

单机内存锁不够，推荐 Redis 计数信号量。伪代码：

```js
async function acquireSemaphore(redis, key, limit, ttlMs, owner) {
  const now = Date.now();
  const expiresAt = now + ttlMs;

  await redis.zremrangebyscore(key, 0, now);
  const count = await redis.zcard(key);
  if (count >= limit) return null;

  await redis.zadd(key, expiresAt, owner);
  await redis.pexpire(key, ttlMs);

  return async () => {
    await redis.zrem(key, owner);
  };
}
```

执行任务时：

```js
const owner = `${workerId}:${taskId}`;
const releases = [];

try {
  releases.push(await acquireSemaphore(redis, "lock:global:image", globalLimit, ttlMs, owner));
  releases.push(await acquireSemaphore(redis, `lock:user:${userId}:image`, userLimit, ttlMs, owner));
  releases.push(await acquireSemaphore(redis, `lock:apikey:${keyHash}:image`, keyLimit, ttlMs, owner));

  if (releases.some((release) => !release)) {
    throw new RetryLaterError("concurrency_limited");
  }

  await runGenerationTask(task);
} finally {
  await Promise.allSettled(releases.filter(Boolean).map((release) => release()));
}
```

生产环境可以使用成熟队列库，例如 BullMQ。BullMQ 本身管任务队列，Redis 信号量负责更细的用户和渠道并发。

## 12. 任务队列设计

### 12.1 为什么不要所有请求都同步等待

当前本地版 `/api/images` 和 `/api/generate-outfit` 会直接等待渠道返回。网页版可以保留短任务同步，但更稳的方式是：

- API 立即创建任务并返回 `taskId`。
- 前端用 `taskId` 轮询或 SSE/WebSocket 获取状态。
- Worker 后台执行。

好处：

- 页面刷新后任务不丢。
- 排队状态可见。
- 失败可重试。
- 多服务器部署不会串任务。
- 批量任务更容易管理。

## 15. 安全规则

### 15.1 API Key 安全

必须做到：

- 前端不展示完整 Key。
- 数据库不保存明文 Key。
- 服务端日志不写明文 Key。
- 任务日志只写 `api_key_hash` 的短摘要。
- 管理后台也不能直接看用户完整 Key。

### 15.2 图片访问安全

用户图片默认私有：

```text
access_mode=private
```

访问方式：

1. 前端请求 `/api/images/:imageId/signed-url`。
2. 后端验证 `image.user_id === 当前用户`。
3. 生成 5-30 分钟有效的签名 URL。
4. 前端用签名 URL 展示或下载。

不要把私有图片直接做永久公开 CDN 链接。

### 15.3 防止越权访问

所有涉及用户数据的接口必须检查：

```text
当前登录 user_id == 数据归属 user_id
```

包括：

- 任务详情。
- 图片详情。
- 历史列表。
- 删除任务。
- 下载图片。
- 重新生成。
- 查看日志。

### 15.4 防止重复提交

前端按钮运行中要禁用，但不能只靠前端。

后端增加 `idempotency_key`：

```text
Idempotency-Key: 前端生成的一次提交 ID
```

数据库保存：

```sql
UNIQUE(user_id, idempotency_key)
```

同一个用户短时间重复提交同一个 key，直接返回原任务 ID。

5. 日志里统一写 `taskId`。

验收：

- 每次生成都能在数据库查到任务。
- 失败任务也有记录。
- 前端结果卡展示任务 ID。

### 第 4 阶段：图片对象存储和归属

目标：图片不再混在本地 `data` 目录。

步骤：

1. 接入对象存储。
2. 新增 `task_images` 表。
3. 上传图进入：

```text
users/{user_id}/tasks/{task_id}/inputs/
```

4. 生成图进入：

```text
users/{user_id}/tasks/{task_id}/outputs/
```

5. 前端展示图片时请求签名 URL。
6. 历史记录改为从数据库和对象存储读取。

验收：

- 用户 A 的图片路径带用户 A 的 `user_id`。
- 用户 B 无法访问用户 A 图片签名 URL。
- 删除任务后前端不可见。

### 第 5 阶段：Redis 队列和并发锁

目标：多人同时出图时不乱、不串、不把渠道打爆。

步骤：

1. 接入 Redis。
2. 引入任务队列，例如 BullMQ。
3. API 服务只负责创建任务和入队。
4. Worker 服务负责执行任务。
5. 实现锁：

```text
global lock
user lock
channel lock
apikey lock
task lock
```

6. 设置用户并发限制。
7. 设置批量任务子任务并发限制。
8. 增加卡住任务扫描器。

验收：

- 同一用户超过并发限制时进入排队。
- 两个用户互不串图。
- 同一任务不会被两个 Worker 重复执行。
- Worker 崩溃后锁会过期，任务能失败或重试。

### 第 6 阶段：历史记录和作品库

目标：替代本地 `data/history.json`。

步骤：

1. 新增 `/api/library` 或改造 `/api/history`。
2. 只查询当前用户任务和图片。
3. 增加分页。
4. 增加按来源筛选。
5. 增加批量下载。

验收：

- 用户刷新浏览器后历史仍存在。
- 换电脑登录后仍能看到自己的作品。
- 看不到别人作品。

### 第 7 阶段：CDN 正式发布

目标：前端静态资源从 CDN 访问。

步骤：

1. 准备生产环境变量：

```text
VITE_API_BASE_URL=https://api.jingyinai.com
```

2. 构建前端：

```powershell
npm run build
```

3. 上传 `dist` 到对象存储。
4. 刷新 CDN。
5. API 服务部署到服务器。
6. Nginx 配置 HTTPS 和反代。
7. 验证登录、出图、历史、图片展示。

验收：

- `https://www.jingyinai.com` 打开速度正常。
- 刷新任意前端路由不 404。
- 静态资源命中 CDN。
- API 不被 CDN 错误缓存。

### 第 8 阶段：监控、审计和运营后台

目标：上线后可排查、可管理。

步骤：

1. 管理后台按任务 ID 搜索。
2. 查看用户任务列表。
3. 查看任务事件。
4. 查看渠道错误。
5. 查看并发锁状态。
6. 查看用户额度。
7. 支持管理员手动退款或重试。

验收：

- 用户反馈问题时，能通过任务 ID 查到全过程。
- 能知道失败是用户参数、渠道、超时、锁、保存还是系统错误。

```text

```

## 19. 验收清单

### 19.1 归属验收

- 用户 A 登录后生成一张图。
- 用户 B 登录后访问用户 A 的 `taskId`，必须返回 404 或 403。
- 用户 B 不能看到用户 A 的历史。
- 用户 B 不能下载用户 A 的图片。
- 对象存储里用户 A 图片路径带用户 A 的 `user_id`。

### 19.2 并发锁验收

- 免费用户连续提交 5 个任务，只能同时跑 1 个，其余排队。
- 两个用户同时提交任务，各自按自己的并发限制执行。
- 同一把 API Key 超过限制时排队或重试。
- Worker 崩溃后锁自动过期。
- 卡住任务能被扫描器标记为 `timeout` 或重新入队。

### 19.3 任务 ID 验收

- 前端任务卡展示任务 ID。
- 任务 ID 能在数据库查到。
- 任务 ID 能在日志查到。
- 任务 ID 能关联输入图和输出图。
- 失败任务也有任务 ID 和错误原因。

### 19.4 CDN 验收

- 首页从 CDN 打开。
- `assets/*.js` 和 `assets/*.css` 命中 CDN 缓存。
- `index.html` 更新后能及时刷新。
- 前端刷新子路由不 404。
- API 请求没有被 CDN 静态缓存。

### 19.5 出图链路验收

- 快捷生成无参考图成功。
- 快捷生成带参考图成功。
- 批量换装成功。
- 局部回贴成功。
- 换背景成功。
- 换脸成功。
- 一键详情主图成功。
- 生成图进入当前用户作品库。

## 21. 一句话原则

网页版上线后，所有出图都必须遵守这条规则：

```text
浏览器只负责提交和展示；
服务端负责身份、任务、锁、存储、归属；
数据库记录谁发起；
对象存储记录图片在哪里；
Redis 保证并发不乱；
taskId 贯穿全链路。
```

做到这几点，这套本地源码就能从“一个人电脑上的画板”稳定升级成“多人在线使用的网页版画板”。
