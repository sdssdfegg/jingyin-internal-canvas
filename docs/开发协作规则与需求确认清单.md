# 开发协作规则与需求确认清单

适用目录：`D:\RJ\静音AI绘画V5（源码）`

创建日期：2026-08-13

这份文档用于约定后续怎么开发这个 AI 画板项目。目标是让每一次修改都有记录，每一个新功能都有归属，每一轮开发都知道先确认什么、做什么、怎么验收。

## 1. Git 协作规则

### 1.1 每次修改自动提交

后续约定：

- 每次 Codex 修改项目文件后，默认自动执行一次 Git commit。
- commit 前先查看 `git status`，确认没有混入无关文件。
- commit 前尽量运行与改动匹配的检查，例如服务端改动运行 `D:\RJ\node\npm.cmd run check`。
- commit 信息使用简短中文或英文均可，但要能看出本次改了什么。
- 如果本次改动只是分析、查看、运行命令，没有改文件，则不提交。
- 如果用户明确要求“先不要提交”，则本次不自动 commit。

### 1.2 提交信息建议

常用格式：

```text
docs: 更新项目规范文档
chore: 调整 git 忽略规则
feat: 增加批量换装某功能
fix: 修复快捷生成局部回贴问题
refactor: 拆分快捷生成 API 调用
style: 统一按钮和弹窗样式
build: 调整发布打包脚本
```

### 1.3 分支规则

当前仓库初始分支是 `master`。后续如果进入持续开发，建议：

```text
master                 稳定基线
codex/docs-plan        文档和规划
codex/quickgen-refactor 快捷生成拆分
codex/outfit-refactor   批量生成拆分
codex/release-win       发布包相关
```

如果只是小改动，可以先继续在 `master` 上做；如果是大拆分，建议先开 `codex/...` 分支。

## 2. 后续开发总流程

每次开发按这个顺序：

1. 明确本次目标。
2. 判断属于哪个模块。
3. 查看相关源码和文档。
4. 列出影响范围。
5. 做最小必要修改。
6. 运行检查。
7. 更新文档或版本记录。
8. Git commit。
9. 总结改动和验证结果。

## 3. 需求确认总清单

后续为了让开发有条理，需要逐步和你确认以下信息。

### 3.1 产品定位

需要确认：

- 这个画板主要服务谁：你自己内部用、团队用、客户用、电商客户用，还是作为可销售软件？
- 最核心的用户场景是什么：批量换装、局部回贴、快捷修图、详情主图、图片编辑，还是全部都要？
- 未来最想让用户每天高频使用的是哪个页面？
- 这个工具更偏“专业工作台”，还是“简单傻瓜式生成器”？
- 后续是否需要账号、会员、授权码、试用期、设备绑定？

为什么要确认：

产品定位决定 UI 密度、功能入口、默认参数、是否需要防误操作、是否需要发布包授权。

### 3.2 功能优先级

需要把功能分成三档：

```text
P0：必须稳定，坏了就不能用
P1：重要，但可以逐步完善
P2：想法功能，可后续排期
```

建议当前先这样分：

P0：

- 快捷生成。
- 批量换装。
- 局部回贴。
- 保存目录。
- 图片下载。
- 历史记录。
- API Key 设置。

P1：

- 批量换背景。
- 批量换脸。
- 设计稿。
- 批量改尺寸。
- 参考生图。
- 一键详情主图。
- 图片编辑。
- AI 质检。

P2：

- 无限画布。
- 素材库。
- 多账号。
- 云端同步。
- 模板市场。
- 自动排版。
- 批量任务统计。

需要你确认：这个分级是否符合你的真实业务。

### 3.3 页面和入口规划

需要确认：

- 左侧导航最终保留哪些一级入口？
- “批量生成”内部应该保留哪些页签？
- “局部回贴”是作为批量页内部页签，还是未来要独立成一级入口？
- “图片编辑”和“批量改尺寸”是一个工具箱，还是独立页面？
- “参考生图”和“详情主图”是否还要继续保留？
- 是否需要一个“首页/工作台概览”展示最近任务和常用入口？

建议先不要做营销首页，继续保持工具打开即工作台。

### 3.4 批量生成业务规则

这是最需要确认的部分，因为它直接影响出图效果。

需要确认：

- 批量换装里图1、图2、图3的固定定义是什么？
- 图3默认是否继续保持“不参与，除非提示词明确提到图3”？
- 局部回贴页中图2是只做结构参考，还是可以影响颜色/材质？
- 换背景页中图1和图2分别代表什么？
- 换脸页中图1和图2分别代表什么？
- 设计稿页到底是生成线稿、服装结构稿、还是实拍补充图？
- 批量姿态页是否要继续放在批量生成内部？
- 自定义页是否允许完全不套 SKILL？

需要沉淀为文档：

```text
docs/提示词规则边界.md
```

### 3.5 局部回贴规则

需要确认：

- 局部回贴优先推荐矩形，还是涂抹蒙版？
- 对客户来说，“普通裁剪”和“局部回贴”是否容易混淆？
- 是否需要在 UI 上明确区分“裁剪参考”和“生成后贴回原图”？
- GPT、香蕉、香蕉2 的局部回贴是否继续保留不同后处理策略？
- 是否要把局部回贴做成一个更独立、更清晰的流程？

### 3.6 模型和渠道策略

需要确认：

- 后续主推哪个模型：`gpt-image`、`nano-banana-pro`、`nano-banana2`、`nano-banana`？
- 哪些模型给客户开放，哪些只内部测试？
- 失败时是否继续自动切换备用渠道？
- 是否允许用户自己填 baseUrl，还是固定用内置渠道？
- 是否需要在 UI 上显示渠道耗时、失败原因、重试次数？

### 3.7 图片规格和保存规则

需要确认：

- 默认尺寸继续用 `2K` 吗？
- 常用比例保留哪些：`1:1`、`3:4`、`4:3`、`16:9`、`9:16` 是否足够？
- 保存文件命名规则是否继续使用每日编号？
- 不同模块是否保存到不同子文件夹？
- 批量改尺寸导出默认保存到哪个文件夹？
- 是否需要一键打开当天生成目录？

### 3.8 历史和素材库

需要确认：

- 历史记录最多保留多少张？
- 是否需要按模块筛选历史：快捷、批量、详情、参考？
- 是否需要搜索历史提示词？
- 素材库是否要成为正式功能？
- 是否需要收藏、标签、项目分组？
- 客户发布包是否默认清空历史？

### 3.9 UI 风格

需要确认：

- 暗色主题是否是默认主风格？
- 是否需要亮色主题？
- UI 更偏专业密集，还是简洁大按钮？
- 批量页面底部固定操作栏是否作为永久规则？
- 上传区是否要统一成三列：图1、图2、图3？
- 结果区卡片是否统一操作按钮？

### 3.10 发布和客户交付

已确认：

- 当前优先发布 Windows EXE。
- 发布包目录名称改为 `静音AI绘画-WIN（V5）`。
- 发布包不携带 `.env`、KEY、`data`、`logs`、上传图、历史图、生图记录和本机运行日志。
- 发布包保留默认提示词和页面预设。
- 每次发布都在 `docs/发布包记录.md` 记录 EXE 的 SHA256。

仍需确认：

- 是否还要源码版、本地网页版。
- 是否需要常见问题、演示图。
- 是否需要内置自动更新。
- 是否需要授权、试用期或设备绑定。

### 3.11 安全和隐私

需要确认：

- API Key 只存在本机，还是未来要有服务端托管？
- 客户生成图片是否只保存在本机？
- 日志是否允许记录提示词和图片地址？
- 发布版是否继续禁用生成日志？
- 是否需要一键清理缓存和历史？

### 3.12 技术规范

需要确认：

- 是否使用 TypeScript，还是继续 JavaScript？
- 是否引入测试框架？
- 是否允许大重构，还是只做渐进拆分？
- 是否保留 Vite + Express 架构？
- 是否未来做 Electron/Tauri 桌面壳？
- 是否需要多语言？

当前建议：

- 继续 JavaScript，不急着上 TypeScript。
- 继续 Vite + Express。
- 先做渐进拆分。
- 先用人工验收清单，不急着引入复杂测试。

## 5. 当前推荐路线

结合当前源码状态，最稳路线是：

```text
先文档化
-> 再统一 Git 和验收
-> 再抽 API client
-> 再抽通用工具函数
-> 再拆快捷生成
-> 再拆批量生成
-> 最后拆服务端核心出图接口
```

第一阶段不要急着改变界面，也不要急着改提示词。先让项目结构和协作方式稳定下来。

## 6. 每轮开发结束必须回答

每轮结束时，Codex 应该给出：

- 改了哪些文件。
- 做了什么。
- 有没有运行检查。
- commit id 是什么。
- 有没有未完成风险。
- 下一步建议。

这样项目会一直保持可追踪。
